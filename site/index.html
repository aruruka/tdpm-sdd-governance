The Architectural Reality

Why Autonomous Coding Agents Break Production Architectures

When AI models write code unconstrained, architectural integrity dissolves into technical debt.

⚡

Premature Implementation Rush

Agents jump straight to database schemas and HTTP handlers before domain rules are settled. They assume business requirements rather than verifying edge cases with domain stakeholders.

🔓

Leaky Aggregate Encapsulation

LLMs expose internal aggregate state through public getters to satisfy queries. This breaks consistency boundaries and entangles write models with reporting layers.

💥

Dual-Write Split-Brain Failures

Unconstrained agents issue separate database mutations and message queue calls. Without transactional outbox patterns, network glitches corrupt state across distributed boundaries.

🌪️

Silent Specification Drift

When implementations diverge, agents modify unit test assertions to match broken code. Upstream specifications lose authority, leaving codebases unmaintainable.

The Governance Solution

Meet tdpm-sdd-governance: Causal Phase Gates for Antigravity Agents

A Google Antigravity plugin enforcing the Technical Director and Product Manager engineering partnership at the tool-execution layer.

Orchestration

@td-pm Principal Orchestrator

Reads the state ledger (.agents/state/phase-lock.json), enforces phase precedence, and delegates to specialized subagents based on active phase ownership.

Product Ownership

@pm-planner Product Manager

Drives Phase 0 legacy brownfield triage, Phase 1 ubiquitous language context maps, and Phase 2 multi-round Socratic BDD dialogue via the ask_question tool.

Architecture Authority

@td-auditor Technical Director

Enforces Bridge 2.5b pattern selection, Phase 3 tactical DDD stubs, Phase 4 OpenAPI/AsyncAPI/DDL contracts, and Phase 5 inside-out Red-to-Green implementation.

Deterministic Protection

PreToolUse Hook Enforcement

Physically intercepts all file writes, edits, and shell commands. Denies premature code authoring and blocks modifications to cryptographically locked artifacts.

Real-World Developer Workflows

Interactive Developer Playbook: go-cqrs in Action

Explore how human developers collaborate with @td-pm, @pm-planner, and @td-auditor across feature delivery and bug patching.

Scenario

You need to add a net-new transfer module (for inter-account fund transfers) to an existing go-cqrs service (./modern-service) without allowing the AI agent to skip specifications or leak domain internals.

  1. Step 1

    Initial Entrypoint: Register Module with @td-pm

    Start with @td-pm (Principal Orchestrator) or trigger /sdd-bdd-architect. Register the module at Phase 1 (skipping Phase 0 brownfield triage for net-new greenfield features):

    CLI Command 
    uv run --directory "$PLUGIN_HOME" python -m tdpm_sdd.cli add-module \
  --workspace ./modern-service \
  --module transfer \
  --language go \
  --phase 1 \
  --activate

    Lifecycle Guard: The PreInvocation hook immediately renders the status banner into the conversation, and PreToolUse physically blocks premature writes to .go, .feature, or .sql files.

  2. Step 2

    Phase 1: Strategic DDD & Context Mapping

    @td-pm delegates work to @pm-planner and @td-auditor to define architectural boundaries:

    • docs/architecture/boundary-map.md: Define Ubiquitous Language Glossary, Subdomain classification (Core vs Supporting), and Context Map relationships (OHS, PL, SK, ACL).
    • specs/ddd/arch-rules.yaml: Lock forbidden cross-boundary Go package imports.
    • docs/architecture/ARCHITECTURE_BLUEPRINT.md: Document topology diagrams (Go code snippets capped at ≤15 lines by SDD-BLUEPRINT-NO-CODE-DUMP).

    Gate G1 Transition: Run tdpm-sdd verify-gate → developer approves scorecard via ask_question → run:

    tdpm-sdd promote-phase --workspace ./modern-service --module transfer \
  --lock-files "docs/architecture/boundary-map.md" "specs/ddd/arch-rules.yaml"
  3. Step 3

    Phase 2: Socratic BDD Dialogue & Bridge 2.5b Pattern Gate

    @pm-planner conducts structured Example Mapping in specs/bdd/example-map.md and interviews the developer through at least 2 rounds of ask_question, logging each round:

    tdpm-sdd record-dialogue --workspace ./modern-service --module transfer --round 1 --unresolved-questions 2
tdpm-sdd record-dialogue --workspace ./modern-service --module transfer --round 2 --unresolved-questions 0

    Next, @td-auditor documents the Event Modeling timeline and executes the Bridge 2.5b Tactical Pattern Gate:

    uv run --directory "$PLUGIN_HOME" python -m tdpm_sdd.cli select-pattern \
  --workspace ./modern-service \
  --module transfer \
  --paradigm CQRS_EVENT_SOURCING \
  --scope PROCESS_MANAGER_SAGA

    Once approved, @pm-planner authors specs/features/transfer.feature in pure Ubiquitous Language (Given events / When command / Then emitted events or domain errors—zero HTTP/SQL leakage). Then promote through Gate G2.

  4. Step 4

    Phase 3: Tactical DDD Stubs & Ports (SDD_STUB)

    Active ownership switches to @td-auditor (skill: /sdd-tactical-contract). Translates transfer.feature 1:1 into Go domain types under internal/transfer/...:

    • Sealed Aggregates: Strictly private/unexported fields (public getters blocked by DDD-SEALED-AGGREGATE-GETTER).
    • Value Objects: Currency represented as int64 cents (float types blocked by DDD-FLOAT-CURRENCY).
    • Method Stubs: Every function body must be a single-line panic stub: 
      panic("SDD_STUB: implementation locked until Phase 5b")

    Promote through Gate G3, locking tactical documentation and stubs.

  5. Step 5

    Phase 4: Interface & Storage Contracts

    Production Go source files are frozen. @td-auditor and @pm-planner lock technical contracts:

    • specs/openapi/transfer.v1.yaml (OpenAPI 3.1 HTTP contract)
    • specs/asyncapi/transfer-events.v1.yaml (AsyncAPI 3.0 event payload contract)
    • migrations/**/*.sql (PostgreSQL 16 idempotent DDL)
    • docs/uat/UAT_PLAYBOOK.md (Pre-implementation user acceptance playbook)

    Promote through Gate G4 to advance to Phase 5a_RED_HARNESS.

  6. Step 6

    Phase 5: Red-to-Green Implementation

    Sub-Phase 5a

    Red Test Harness

    Agent writes only *_test.go files. Tests must compile (go test -c ./... exits 0) and fail against SDD_STUB panics. Lock tests and advance to 5b.

    Sub-Phase 5b

    Inside-Out Implementation

    Replaces stubs inside-out: Domain Aggregate → Event Store & Outbox → Projections → HTTP Routers. Upstream contracts remain cryptographically locked.

    Sub-Phase 5c

    Verification & Cutover

    Executes concurrency suites, race detection, and publishes benchmark evidence in docs/architecture/CUTOVER_AND_BENCHMARK_REPORT.md.

  7. Step 7

    4-Point Completion Criteria

    A module is verified 100% complete when all four independent criteria pass:

    ✓

    1. State Ledger Check

    tdpm-sdd status reports current_phase: 5, sub_phase: "5c_VERIFICATION", and gates_passed: ["G1", "G2", "G3", "G4", "G5"].

    ✓

    2. Deterministic Gate Audit

    tdpm-sdd verify-gate exits 0 with "passed": true, 0 AST errors, and 0 remaining SDD_STUB panics.

    ✓

    3. Go Race Test Suite

    go test -v -race ./internal/transfer/... ./test/verification/... passes 100% with zero data races.

    ✓

    4. Read-Only SDK Verification

    @sdk-architect confirms end-to-end traceability and 100% SHA-256 cryptographic lock integrity via FastMCP.

Scenario

An existing module (account) is at Phase 5 (5c_VERIFICATION) with all production code and test files sealed by SHA-256 locks. A production edge-case bug requires a patch without breaking upstream contracts.

  1. Step 1

    Entrypoint: Invoke @td-auditor & Inspect Status

    Invoke @td-auditor with skills /systematic-debugging and /strict-audit to diagnose the root cause:

    CLI Command 
    uv run --directory "$PLUGIN_HOME" python -m tdpm_sdd.cli status --workspace ./modern-service

    Confirm the module is locked and identify which specific domain invariant failed.

  2. Step 2

    Controlled Unlocking & Red-First Bug Patching Workflow

    Because tests and code are locked in phase-lock.json, silent ad-hoc fixes are blocked:

    Action 2.1

    Write Regression Test First

    Target account_test.go. PreToolUse triggers a force_ask human approval checkpoint. Approve the edit and verify go test fails on the new regression test.

    Action 2.2

    Apply Root-Cause Fix in Code

    Edit production code (e.g. postgres_read_repo.go). PreToolUse prompts for human approval while running static AST checks to block leaky shortcuts.

    Action 2.3

    Re-Seal SHA-256 Locks

    Re-lock modified artifacts so verify-gate captures the new canonical SHA-256 checksums and clears SDD-LOCK-DRIFT:

    tdpm-sdd promote-phase --workspace ./modern-service \
  --module account \
  --lock-files "internal/account/**/*.go" "test/verification/*_test.go" \
  --force
  3. Step 3

    4-Step Verification Checklist

    Confirm the bug fix is robust and regression-free before merging:

    ✓

    1. Red → Green Proof

    The new test failed before the fix and passes consistently under go test -v -race ./....

    ✓

    2. Deterministic Gate Audit

    tdpm-sdd verify-gate returns "passed": true with 0 AST findings and 0 lock-drift errors.

    ✓

    3. Read-Only Invariant Audit

    @sdk-architect confirms OpenAPI/AsyncAPI schemas and outbox idempotency remain intact.

    ✓

    4. Concurrency Suite

    Parallel withdrawals, event replays, and outbox retries pass cleanly with zero data races.

Clear Answers

Frequently Asked Questions

Self-contained answers for engineers, architects, and AI answer engines.

What is tdpm-sdd-governance? ▾

tdpm-sdd-governance is an open-source Google Antigravity plugin providing stage-gated Spec-Driven Development. It pairs Product Manager and Technical Director subagents with deterministic lifecycle hooks, cryptographic SHA-256 locks, and static AST auditors to prevent AI agent code rot.

How does tdpm-sdd-governance prevent premature code generation? ▾

The plugin uses a PreToolUse hook that blocks write operations to implementation files until prior phases are completed. Agents cannot write Go code before BDD scenarios and tactical DDD stubs are sealed.

Which programming languages and tactical paradigms are supported? ▾

tdpm-sdd-governance primarily targets Go 1.23+ with first-class support for CQRS and event sourcing. It also provides parameterized audit rules for Python and TypeScript across state-based concurrency and vertical-slice CRUD paradigms.

Can I modify locked specifications or tests after gate promotion? ▾

Yes. Modifying locked artifacts triggers a force-ask prompt requiring developer approval. After applying modifications, running promote-phase with the force flag re-seals the cryptographic SHA-256 digests in the state ledger.

Does tdpm-sdd-governance send code or telemetry to third-party servers? ▾

No. tdpm-sdd-governance operates 100% locally on your machine. All lifecycle hooks, state ledger updates, AST audits, and verification tools execute locally through Python and the Google Antigravity runtime.

How does the Socratic BDD Example Mapping dialogue work? ▾

In Phase 2, the Product Manager subagent asks structured domain questions using the ask_question tool. The plugin enforces at least two recorded dialogue rounds before unlocking Gherkin feature file authoring.

How do I verify that my feature implementation is complete? ▾

Run tdpm-sdd verify-gate to confirm zero AST findings and zero lock drift. Then execute the Go race test suite and run the read-only sdk-architect audit to verify end-to-end traceability.
